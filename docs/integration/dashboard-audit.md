## 5. x402 Protocol Version & Headers Analysis

### Current Status in Repo: **x402 V1**
- Challenge header: Returns HTTP `402 Payment Required` with body:
  ```json
  { "x402Version": 1, "error": "X-PAYMENT header is required", "accepts": [...] }
  ```
- Client authorization header: `X-PAYMENT`
- Merchant settlement header: `X-PAYMENT-RESPONSE`

### Target Hackathon Requirement: **x402 V2**
- Challenge: `PAYMENT-REQUIRED` header / v2 challenge body
- Client authorization: `PAYMENT-SIGNATURE` header
- Settlement receipt: `PAYMENT-RESPONSE` header

### Safe Migration Plan (Dual-Header Support)
To avoid breaking existing x402 V1 client tools (`examples/agent-client.ts`, SDK 1.2.0) while fully supporting V2:
1. **Server Inbound:** Check `PAYMENT-SIGNATURE` first; if not found, inspect `X-PAYMENT`.
2. **Server Outbound:** When client uses V2 (`PAYMENT-SIGNATURE`), respond with `PAYMENT-RESPONSE`. Also emit `X-PAYMENT-RESPONSE` to maintain dual-compatibility.
3. **No Silent Mixing:** A single transaction flow must strictly use corresponding pairs and log the protocol generation.
4. **Environment Toggle:** `X402_VERSION=2` enforces strict V2 validation across all endpoints.

## 8. Critical Event Segregation Model

Per global security rules, three distinct events must never be conflated:

```
[1] POLICY_APPROVED  → Policy engine allowed the spend intent
        ↓ (only if allowed)
[2] SIGNER_INVOKED   → Local wallet signed EIP-3009 TransferWithAuthorization
        ↓ (only if signed & submitted)
[3] FUNDS_TRANSFERRED → Neutral mock blockchain confirmed ledger debit
```

- A payment can be approved, but if it violates pinning at L4, the **signer is never invoked**.
- A payment can be signed, but if the facilitator or merchant drops it, **funds never transfer**.
- The mock chain is the **sole source of truth** for funds lost.
